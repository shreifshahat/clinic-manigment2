# القرارات والافتراضات

## 1. قرارات معتمدة (ADR)

### D-01 — بنية تطبيق واحدة مقسّمة إلى وحدات (Modular Monolith)
**القرار:** FastAPI واحد + Next.js واحد + PostgreSQL واحد.
**لماذا:** لا حاجة مثبتة لخدمات مصغّرة: نطاق واحد، قاعدة بيانات واحدة، فريق
صغير. التقسيم إلى وحدات داخل العملية يبقى قابلًا للاستخراج لاحقًا إن فرضته
الحِمل، دون تكلفة تشغيلية الآن.
**النتيجة:** `backend/app/{core,db,models,schemas,services,api}`.

### D-02 — المصادقة عبر Supabase Auth حصرًا
**القرار:** لا تجزئة كلمات مرور داخل النظام؛ التحقق من JWT مقابل JWKS.
**لماذا:** المواصفة نصّت على عدم بناء نظام مصادقة خاص. Supabase يوفّر Argon2
وحدود محاولات وPITR وMJ/logout.
**الأثر:** نحتاج دور `clinic_app` + `service_role` في الخلفية، و`anon` في
الواجهة فقط.

### D-03 — RLS كطبقة ثانية، مع دور قاعدة بيانات غير مالك
**القرار:** التطبيق يتصل بدور `clinic_app` (لا يملك الجداول) → RLS تنطبق
دائمًا.
**لماذا:** لو استُخدم دور `postgres` لتجاوز RLS لANNEEWould تُلغى الطبقة الثانية
كليًا.
**ملاحظة:** `FORCE ROW LEVEL SECURITY` **غير مفعّل** عمدًا: الدوال المساعدة
`SECURITY DEFINER` مملوكة لمالك الجداول، و`FORCE` كان سيخضعها للسياسات فينكسر
مصافحة الجلسة. موثَّق في `DATABASE.md` §4.

### D-04 — منع التعارض بثلاث طبقات
`pg_advisory_xact_lock` (تسلسل) + إعادة فحص (منطق) + `EXCLUDE USING gist`
(قاعدة). **القرار:** البقاعدة هي المرجع النهائي، حتى الكتابة اليدوية لا تتجاوزها.

### D-05 — لا `DELETE` على السجلات الحسّاسة
**القرار:** الحذف الناعم للمرضى، والإلغاء الموثّق للفواتير والمدفوعات
والمصروفات، و`sessions`/idempotency هي الاستثناءات الوحيدة.
**لماذا:** أثر مالي وسريري يجب أن يكون قابلًا للتدقيق.

### D-06 — المال بـ`Decimal` و`NUMERIC(14,2)`، ويُنقل كنص في JSON
**القرار:** لا `float` في أي طبقة. `Mapped[Decimal]` في النماذج (مُتحقَّق منه بـ
mypy)، و`Decimal` في الخدمات، ونص في الـ API.
**لماذا:** أخطاء الفاصلة العائمة في الحسابات المالية غير مقبولة.

### D-07 — لا تشفير أعمدة للأرقام الشخصية
**القرار:** الاعتماد على RLS + تقليل الحقول + تشفير التخزين لدى Supabase.
**لماذا:** Supabase لا يوفّر TDE على مستوى العمود، والتشفير بمفتاح في
التطبيق (Fernet) يضيف كلفة تشغيلية ويجعل البيانات غير قابلة للاستعلام في
التقارير. **التبعة المقبولة:** من يملك وصولًا إداريًا على القاعدة يستطيع قراءة
الأرقام — لذلك رُفعت `R7` في `SECURITY.md`. **قرار معلّق:** إن تطلّبditor691
التشفير على مستوى العمود، يُقيَّم `pgcrypto` مع إدارة مفاتيح منفصلة.

### D-08 — نافذة التقرير الأسبوعي = 7 أيام تنتهى اليوم
**القرار:** افتراضيًا آخر 7 أيام (شاملة)؛ ويقبل `start`/`end` صراحةً.
**لماذا:** أبسط تعريف قابل للتفسير. بداية الأسبوع التقويمي (السبت) مُعدّة
لـ`WEEK_START_WEEKDAY` لكنها **لا تُستخدم** في نافذة التقرير الحالية — قرار
معلّق (انظر §3).

### D-09 — الواجهة: Next.js App Router + Tailwind + TanStack Query
**القرار:** بناء مكتبة UI صغيرة بدل مكتبة مكوّنات.
**لماذا:** تقليل الاعتماديات والمخاطرة، والتحكم في RTL.

### D-10 — مسار بيانات مباشر مغلق
**القرار:** `REVOKE ALL` من `anon`/`authenticated` على كل الجداول؛ المتصفح
يستعمل `anon` للمصادقة فقط.
**لماذا:** كل البيانات تمر عبر الـ API حيث تعمل الطبقات الثلاث؛ وإبقاء
الوصول المباشر يفتح طريقًا لتجاوز إسقاط الحقول (مثل هاتف المريض لصاحب العيادة).

### D-11 — مصادقة تطوير معطّلة افتراضيًا
**القرار:** `DEV_AUTH_ENABLED=false`، و`DevTokenVerifier` يرفض العمل في
`ENV=production`.
**لماذا:** لازم تشغيل المشروع وتجاربه دون مشروع Supabase، دون فتح باب خلفي
في الإنتاج. **حدود مذكورة:** هذا مسار تطوير مخصّص للاختبارات والاستعراض، وهو
موثَّق في `SECURITY.md`.
