# الأمن والخصوصية

> هذا التقرير يصف **الضوابط المطبَّقة فعلًا** ونقاط الضعف المتبقية.
> لا يُدَّعي أن النظام خالٍ من الثغرات — أي نظام برمجي نقاط ضعف فيه.

## 1. ملخص

| المجال | الحالة | الملاحظة |
|---|---|---|
| المصادقة | ✅ | Supabase Auth (JWKS)، لا كلمات مرور مخزّنة |
| إدارة الجلسات | ✅ | سجل خادمي + إبطال فوري |

## 2. الضوابط المطبَّقة

### 2.1 المصادقة وإدارة الجلسات
- **Supabase Auth** هو نظام المصادقة الوحيد. لا يوجد `password_hash` في أي جدول.
- التحقق من الرمز يتم مقابل **JWKS** (مفاتيح غير متماثلة) — لا مفتاح توقيع في الخادم.
- `staff_sessions` يسمح بـ**إنهاء صلاحية الوصول فورًا**: تسجيل الخروج، تعطيل الحساب،
  إعادة تعيين كلمة المرور. يُفحص في كل طلب.
- `must_change_password` يُجبَر على تغيير كلمة المرور المؤقتة عند أول دخول.
- 创建 الحسابات عبر **Supabase Admin API** من الخلفية فقط (مفتاح `service_role` في
  الخادم، ولا يظهر في المتصفح أبدًا). تُولَّد كلمة مرور مؤقتة عشوائية ولا تُخزَّن.

### 2.2 أقل صلاحية (3 طبقات)
1. **العملية**: `Permission` + `ROLE_PERMISSIONS`، مفحوصة في الـ API وفي الخدمات.
2. **السطر**: سياسات RLS (19 جدولًا).
3. **الحقل**: إسقاط صريح (صاحب العيادة بلا هاتف، الريسبشن بلا بنود فاتورة).

### 2.3 حماية الملف الطبي
- جدول `visits` **لا يملك أي policy** يسمح لصاحب العيادة أو الريسبشن بقراءته.
- الطبيب يقرأ سجلاته + ما فُوِّض له صريحًا (`visit_access_grants`).
- القراءة تُسجَّل في `audit_log` **بالمعرّف فقط** (لاDiagnostic ولا علاج ولا ملاحظات).
- مشغِّلات قاعدة البيانات تمنع تعديل الأعمدة المالية، و`visits` للطبيب فقط.

### 2.4 قاعدة البيانات
- كل الاستعلامات عبر SQLAlchemy/asyncpg (استعلامات مُعدّة، لا سَلسَلة نصوص).
- `EXCLUDE USING gist` يمنع أي تداخل زمني حتى بالكتابة اليدوية.
- RLS مفعّل على كل الجداول؛ دور التطبيق **ليس** مالك الجداول.
- المسار المباشر (PostgREST بـ `anon`) **مغلق**: `REVOKE ALL` على `anon`/`authenticated`.

### 2.5 الشبكة و HTTP
- CORS بقائمة نطاقات صريحة؛ `allow_credentials=False`؛ `*` مرفوض في الإنتاج.
- ترويسات: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`,
  `CSP: default-src 'none'`, `Permissions-Policy`, `HSTS` (في الإنتاج).
- `Cache-Control: no-store` على كل الاستجابات.
- `X-Request-ID` للتتبع.

### 2.6 التسجيل
- سجل JSON لكل طلب: المعرّف، المسار، الحالة، المدة، IP.
- **إخفاء تلقائي** لأي مفتاح حسّاس (`password`, `token`, `diagnosis`, `treatment`,
  `notes`, `full_name`, `phone`, `national_id`, …) في `app/core/logging.py`.
- استثناءات قاعدة البيانات لا تُمرَّر للمستخدم أبدًا؛ الخطأ 500 يعيد `request_id` فقط.
- `audit_log.details` بقائمة مفاتيح مسموحة (whitelist) → لا محتوى طبي ولا اسم مريض.

### 2.7 الاتصال خارج النظام
- **النظام لا يرسل أي رسالة** (بريد، SMS، إشعار) لأي شخص — لا المرضى ولا
  الزملاء. لا يوجد «إرسال تأكيد» ولا «تنبيه الموعد».
- **الاستثناء الوحيد** هو مزوّد المصادقة نفسه: Supabase Auth قد يرسل بريد
  استعادة كلمة المرور أو دعوة ضبطها إذا فُعّل SMTP. هذه رسالة **نظامية** من
  المزوّد، ولا تتضمن بيانات مرضى (البريد واسم الموظف فقط).
- لا يوجد أي اتصال صادر من الخلفية عدا: Supabase Auth (JWKS + Admin API).

### 2.8 الأسرار
- كل الأسرار في متغيرات البيئة؛ `.env.example` بلا أي قيمة حقيقية.
- `DEV_AUTH_SECRET` و`service_role` **ممنوعان في الإنتاج** (حارس في
  `app/core/auth/factory.py` يرفض العمل بدون Supabase في `ENV=production`).

## 3. الضوابط التي يوفّرها Supabase (خارج حدود كودنا)

| الضابط | الملاحظة |
|---|---|
| حد محاولات الدخول | Supabase يطبّق حدًّا على محاولات الدخول حسب IP والبريد. نحن **لا نرى** المحاولات الفاشلة (لأن المصادقة في المتصفح)، فلا يمكننا ربطها بسجل التدقيق أو حظرها داخليًا. **حدود معروفة.** |
| تخزين كلمات المرور | Argon2/BCrypt داخل Supabase (خارج نطاق كودنا). |
| TLS | مشفّر بين Supabase والخادم عبر رابط الاتصال المباشر. |

## 4. المخاطر المتبقية (نقطة صدق)

| # | الخطر | الأثر | الاحتمال | التخفيف الحالي | ما هو مطلوب |
|---|---|---|---|---|---|
| R1 | **حد الطلبات داخل الذاكرة** | في نشر متعدد العمليات/النسخ، الحد الفعلي = الحد × عدد العمليات | متوسط | حد 120/دقيقة لكل IP | نقل العدّاد إلى Redis/قاعدة، أو نشر نسخة واحدة |
| R2 | **Session fixation عبر رمز مسروق** | استخدام رمز صالح حتى انتهاء صلاحيته | منخفض | إبطال فوري عبر `staff_sessions` | تدوير الرمز بعد تغيير كلمة المرور (مطبَّق) |
| R3 | **تسريب بيانات عبر السجلات** | اسم/هاتف/تشخيص في log | منخفض | إخفاء تلقائي + whitelist | مراجعة أسبوعية للسجلات في الإنتاج |
| R4 | **حقن SQL مستقبلي** | أي استعلام نصي جديد | منخفض | مراجعات + lint | مراجعة كود إلزامية قبل كل دمج |
| R5 | **عامل خبيث في المتصفح (XSS مخزّن)** | تنفيذ في جلسة الموظف | منخفض | React يهرّب + لا `dangerouslySetInnerHTML` | مراجعة الكود + CSP على الواجهة عند النشر |
| R6 | **تسريب مفتاح `service_role`** | وصول كامل لقاعدة البيانات | منخفض | المفتاح في الخادم فقط | تدوير دوري + مراقبة استخدام المفتاح |
| R7 | **الوصول المباشر للمستخدم لـ DB console في Supabase** | تجاوز RLS (المالك يتجاوزها) | متوسط | RLS + أدوار | قصر الوصول على مالكين محدودين + سجلات دخول |
| R8 | **غياب اختبار اختراق مستقل** | ثغرات منطقية غير مغطاة | متوسط | 96 اختبارًا آليًا (62 خلفية + 34 واجهة) | اختبار اختراق مستقل قبل الإنتاج |
| R9 | **سوء إعداد CORS في الإنتاج** | طلبات من نطاقات غير مصرّحة | منخفض | حارس يرفض `*` | مراجعة إعداد الإنتاج |
| R10 | **نقص خطة استعادة مُختبَرة** | فقد بيانات عند حادث | متوسط | موثَّق | تنفيذ اختبار استعادة ربع سنوي |

## 5. ما لا يمكن ضمانه

- لا يمكن ضمان غياب الثغرات completely؛ الضوابط Reduce الاحتمال ولا تلغيه.
- RLS **لا تمنع** مالك قاعدة البيانات (Supabase `postgres`) — هو يتجاوزها بالتصميم.
- تشفير الأعمدة على مستوى العمود (مثل أرقام الهواتف) **غير مطبَّق**: الجداول على
  Supabase لا تدعم TDE على مستوى العمود. الحماية تعتمد على RLS + التقليل من الحقول
  + تشفير القرص/التخزين لدى Supabase. (انظر `DECISIONS.md` → D-07.)
- النظام **لا يراقب** سلوك المستخدم داخله (لا كشف شذوذ) — سجل التدقيق للاست事后
  وليس للكشف الفوري.
