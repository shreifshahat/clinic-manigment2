# المعمارية والتقنيات

## 1. قرار التقنيات ولماذا

### الخلفية: Python + FastAPI

| الخيار | القرار | السبب |
|---|---|---|
| **FastAPI** | ✅ المعتمد | توثيق OpenAPI **تلقائي** من نفس تعريف المسارات (بند 8)، تحقق صارم عبر Pydantic v2، وحقن اعتماديات (DI) طبيعي لتطبيق الصلاحيات. |
| Flask | ❌ | كل شيء يُبنى يدويًا: التحقق، التوثيق، الـ DI. تكلفة صيانة أعلى والمخاطرة أكبر. |
| Django + DRF | ❌ | ORM وAdmin ممتازان، لكن المشروع API-فقط؛django-admin وكوده الخلفي زائدان، وRLS وPostgres المتقدم يحتاج SQL خامًا خارج DJango. |
| microservices | ❌ | لا حاجة مثبتة: نطاق واحد، قاعدة بيانات واحدة، فريق صغير. تم اعتماد **وحدة تطبيقية (modular monolith)**. |

**إصدارات مثبّتة** في `backend/pyproject.toml` (كلها بإصدارات دقيقة):

| الحزمة | الإصدار | سبب الحاجة |
|---|---|---|
| `fastapi` | 0.156.0 | إطار ASGI + OpenAPI + DI. |
| `uvicorn[standard]` | 0.54.0 | خادم ASGI للإنتاج. |
| `sqlalchemy[asyncio]` | 2.1.5 | ORM/Core مع معاملات صريحة و `SELECT … FOR UPDATE`. |
| `greenlet` | 3.3.2 | مطلوب لجسر asyncio في SQLAlchemy. |
| `asyncpg` | 0.32.0 | درايفر Postgres غير متزامن (server-side prepared statements). |
| `alembic` | 1.20.0 | ترحيلات متبَّعة وقابلة للمراجعة. |
| `pydantic` / `pydantic-settings` | 2.14.1 / 2.16.1 | تحقق + إعدادات من البيئة. |
| `PyJWT[crypto]` | 2.15.1 | التحقق من JWT مقابل JWKS (بدون تخزين مفتاح توقيع). |
| `httpx` | 0.28.1 | نداءات Supabase Admin API. |
| `email-validator` | 2.3.0 | التحقق من بريد الموظفين. |

أدوات التطوير: `pytest`, `pytest-asyncio`, `pytest-cov`, `ruff`, `mypy`, `pip-audit`.

**لماذا لا توجد حزمة أخرى؟** لا حاجة لمكتبة أرقام (Decimal في المكتبة القياسية)، ولا لمكتبة تواريخ (zoneinfo + Intl)، ولا لمكتبة تحقق إضافية (Pydantic)، ولا لمكتبة ORM إضافية (SQLAlchemy). مكتبة `argon2`/`bcrypt` **لم تُستخدم** عن قصد: لا يوجد تجزئة كلمات مرور داخل النظام (Supabase Auth يملكها).

### الواجهة: Next.js (App Router)

طلبَ المستخدم صراحةً **Next.js**، وقد نُفِّذ. ملاحظات تنفيذية:

- **App Router** مع بنية `src/app` وتوجيه بـ URL لكل دور.
- **Client Components** لصفحات الأدوار (لوحات تفاعلية تحتاج حالة الخادم)، مع Server Components فقط حيث لا حاجة.
- **Tailwind CSS v4** مع أدوات منطقية (`ms-`/`me-`/`ps-`/`pe-`/`text-start`) لدعم RTL أصلي.
- **TanStack Query** لإدارة حالة الخادم (تخزين مؤقت، إعادة محاولة، تعطيل الإرسال المكرر)؛ **React Hook Form + Zod** للنماذج.
- **بدون مكتبة تواريخ**: `Intl.DateTimeFormat` مع المنطقة الزمنية من `GET /api/v1/meta/clinic`.
- **بدون مكتبة مكوّنات**: مجموعة UI صغيرة مكتوبة يدويًا (أزرار، حقول، جداول، بطاقات) لتقليل الاعتماديات والمخاطرة.

│   │   │   ├── money.py         # Decimal فقط
│   │   │   └── timeutil.py      # سياسة المنطقة الزمنية

│   │   ├── models/              # جداول SQLAlchemy (19 جدولاً)
│   │   ├── schemas/             # DTO لكل دور (إسقاط الحقول)
│   │   ├── services/            # منطق الأعمال (لا يعرف HTTP)
│   │   ├── api/
│   │   │   ├── deps.py          # المصادقة، الصلاحيات، وحدة العمل
│   │   │   ├── docs.py          # تعريفات استجابات OpenAPI
│   │   │   └── v1/routers/      # 11 وحدة REST

**فصل المسؤوليات:** الـ routers تقرأ الطلب وتستجيب فقط، الـ services تحتوي قواعد العمل، والـ models/schemas تفصل قاعدة البيانات عن العالم الخارجي. لا تستورد طبقة `services` أي شيء من `api` (عدا `StaffPrincipal` لتمرير هوية المنفّذ)، ولا تستورد `api` أي منطق عمل.

## 3. تدفّق الطلب

```
المتصفح ──Authorization: Bearer <Supabase token>──► FastAPI
   │
   ├─ RequestContextMiddleware  → request_id + ترويسات أمان + سجل JSON
   ├─ RateLimitMiddleware       → حد الطلبات لكل IP
   ├─ CORS                      → نطاقات مسموحة فقط
   │
   ├─ get_token_verifier        → التحقق من JWT مقابل JWKS
   ├─ get_current_staff         → staff + set_config(app.user_id/app.role)
   ├─ _register_session         → تسجيل/فحص الجلسة + إنهاء صلاحية الوصول
   │
   ├─ Router                    → تحقق Pydantic + require_permission
   ├─ Service                   → منطق العمل + كتابة سجل التدقيق
   ├─ PostgreSQL (RLS)          → تصفية الصفوف على مستوى القاعدة
   │
   └─ commit (وحدة عمل واحدة لكل طلب)
```

**وحدة العمل = الطلب.** أي فشل يُلغي المعاملة كاملة (الحجز + سجل التدقيق + أيقونة `Idempotency-Key`)، فلا تبقى حالة نصف مكتملة.

## 4. لماذا هذا التصميم للصلاحيات

1. **إخفاء الأزرار غير كافٍ** — لذلك كل عملية محمية على الخادم (طبقة 1).
2. **التحقق في الخلفية وحده غير كافٍ** — لذلك RLS على مستوى الصف (طبقة 2) حتى لو كُتب كود خاطئ.
3. **RLS وحده لا يكفي للحقول** — لذلك إسقاط صريح حسب الدور (طبقة 3): صاحب العيادة لا يرى هاتف المريض، والريسبشن لا يرى بنود الفاتورة.
4. **البيانات الطبية لها مسار مغلقة** — `visits` لاRwLSelected政策 للطبيب فقط؛ لا يستطيع صاحب العيادة ولا الريسبشن حتى *عدّ* السجلات.

## 5. منع تضارب المواعيد — ثلاث طبقات

| الطبقة | الآلية | ماذا تمنع |
|---|---|---|
| التطبيق | `pg_advisory_xact_lock` على الطبيب | تسلسل عمليات الحجز لنفس الطبيب عبر كل العمليات |
| التطبيق | إعادة فحص التداخل بعد القفل | الحجز في وقت محجوز |
| القاعدة | `EXCLUDE USING gist` على `tstzrange` | أي تداخل — حتى بإدخال يدوي من SQL Editor |
| القاعدة | فهرس فريد جزئي `(doctor, patient, start)` | تكرار الحجز لنفس المريض في نفس الوقت |

إعادة الجدولة = `UPDATE` واحد للصف نفسه (لا حذف+إدخال) داخل معاملة واحدة، مع قفل الطبيب. عند التعارض تُلغى المعاملة فيبقى الحجز الأصلي كما هو تمامًا (مُختبَر).

- الفهارس: `appointments(doctor_staff_id, starts_at)`, `appointments(patient_id, starts_at)`,

## 7. ما **لم** يُنفَّذ عمدًا (نطاق)

- لا بوابة مرضى، ولا تسجيل مريض ذاتي، ولا استشارات فيديو/محادثة.
- لا بوابة دفع إلكترونية ولا PCI DSS (تسجيل الدفع يتم على جهاز الدفع خارج النظام).
- لا ضرائب ولا خصومات ولا استرداد (قرار صريح: خارج الإصدار الأول).
- لا رسائل نصية/بريدية للمرضى ولا للموظفين من داخل النظام (حدود الاتصال الخارجي
  موثّقة في `SECURITY.md` §2.7).
- لا تطبيق موبايل ولا Service Worker (النطاق محدد).
